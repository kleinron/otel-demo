# Expected alerts for scheduled spikes

Use this table after a run to check which alert each spike put into Alerting (Firing). Spikes run daily at 10:00, 12:00, 14:00, and 20:00 UTC. Each spike lasts 20 minutes. The rate multiplier is set by the load generator.

The first spike that actually runs after deploy is a baseline: traffic only, no fault. The expectation is that no alert enters Alerting (Firing). Record what actually happens.

Every later spike is paired with a delay or timeout fault at 100% probability on one operation. The fault starts 2 minutes after the spike starts and lasts 15 minutes. The checkout fault lasts 20 minutes.

Leave the last two columns blank until the run, then fill them in.

The evidence is Grafana alert state history. That history lives inside the Grafana task and is lost on restart. Every alert state change is also sent through a webhook contact point to a small logging endpoint, so it appears as a structured log line in CloudWatch Logs. The event type is `grafana_alert_state_change`, with the rule name, the previous state, the new state, and a timestamp in UTC. Teardown exports those log lines and the Grafana-provisioned rule files. The export fails if neither exists. See [teardown-checklist.md](teardown-checklist.md).

## Notes

- Fault windows must be longer than the rule's evaluation range and `for` duration (the catalog `window`). The state becomes Alerting (Firing) only after the condition has held for `for`.
- The day-2 12:00 UTC spike is the saturation-sized one. Expect CPU saturation visible in metrics in addition to the paired rule, `shop-checkout-p99-latency`, in Alerting (Firing).
- Informational alerts must not page. They route to a no-page contact point.
- Thresholds remain initial values.

## Known gap

Nothing outside Grafana watches Grafana itself, so Grafana-down is not alerted. That is deliberate because alerts are defined in one place. A second watcher would be another alarm system.
