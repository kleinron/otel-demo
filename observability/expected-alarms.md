# Alert hypotheses for scheduled spikes

Alerts are not required to enter Alerting (Firing) during the experiment. The interesting deliverable is how the alerts are configured and tuned: the threshold, the window, and `min_request_count`. This page states a hypothesis for each scheduled spike, then a score sheet to fill after the run.

A missed alert or an extra alert is a finding to write up. It is not a failure of the run.

## Evidence and ground truth

The evidence is Grafana alert state history, together with the `grafana_alert_state_change` log lines teardown exports. That history lives inside the Grafana task and is lost on restart. Every alert state change is also sent through a webhook contact point to a small logging endpoint, so it appears as a structured log line in CloudWatch Logs. The event type is `grafana_alert_state_change`, with the rule name, the previous state, the new state, and a timestamp in UTC. Teardown also exports the Grafana-provisioned rule files. The export fails if neither the log lines nor the rule files exist. See [teardown-checklist.md](teardown-checklist.md).

The logged spike and fault start and end markers, in UTC, are the ground truth for when each window opened and closed. Score rules against those markers. The clock times in the table below are the plan; the log markers are what actually ran.

Time-to-fire is the duration from the fault-window start marker to the first `grafana_alert_state_change` log line whose new state is Alerting (Firing).

## Schedule

Spikes run daily at 10:00, 12:00, 14:00, and 20:00 UTC. Each spike lasts 20 minutes. The rate multiplier is set by the load generator.

The first spike that actually runs after deploy is a baseline: traffic only, no fault.

Every later spike is paired with a delay or timeout fault at 100% probability on one operation. The fault starts 2 minutes after the spike starts and lasts 15 minutes. The checkout fault lasts 20 minutes.

Each hypothesis uses one of these labels:

- **should fire** — the named rule is the paired signal for that fault. Staying quiet is a missed detection.
- **should not fire** — that rule staying out of Alerting (Firing) is the hypothesis. Entering Alerting (Firing) is an extra alert.
- **either is fine** — the signal is borderline. Entering Alerting (Firing) and staying quiet are both acceptable, and either outcome is still written up.

## Scoring

Fill this in after the run. One row per rule in [alerts.yml](alerts.yml). Counts come from the `grafana_alert_state_change` log lines. Windows come from the logged spike and fault start and end markers (UTC).

- **True positives.** Fault windows whose hypothesis for this rule is **should fire**, and the rule entered Alerting (Firing) for that window. Count one per such window.
- **False positives during normal load.** Transitions to Alerting (Firing) outside any fault window, including the baseline spike. The baseline is traffic only.
- **Missed detections.** Fault windows whose hypothesis for this rule is **should fire**, and the rule never entered Alerting (Firing) for that window.
- **Time-to-fire.** From the fault-window start marker to the first log line whose new state is Alerting (Firing). Leave it blank when the rule did not fire. If several fault windows apply, record one duration per window.

**either is fine** is not a true positive and not a missed detection. Record which way it went in the write-up. A **should not fire** rule that enters Alerting (Firing) is an extra alert: count it as a false positive when it falls during normal load, and write it up either way.

`request-rate-zero` uses `missing_data: breaching` (`noDataState: Alerting`). An unplanned silence (a dead runner or broken routing) is a true positive. A planned gap — a known runner restart, or the warm-up before the first spike — is an expected false positive: record it, and do not tune the rule away for that gap. During a spike that is actually sending traffic, this rule **should not fire**.

### Tuning actions per finding

Thresholds in the catalog are initial values. Change the threshold, the window, or `min_request_count`. Leave the finding in the write-up either way.

| Finding                                          | Suggested tuning                                                                                                                                                                                                                         |
| ------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Missed detection                                 | Lower the threshold, shorten the window, or lower `min_request_count`. Use the gate the series failed: the value never crossed the threshold, the breach was shorter than the window, or the window had fewer requests than the minimum. |
| False positive during normal load                | Raise the threshold, lengthen the window, or raise `min_request_count`.                                                                                                                                                                  |
| Extra alert (hypothesis was **should not fire**) | Raise the threshold, lengthen the window, or raise `min_request_count`, the same levers as a normal-load false positive.                                                                                                                 |
| **either is fine**                               | Write up which way it went. Change the threshold, the window, or `min_request_count` only when the write-up shows the rule is measuring a different signal than the one it was tuned for.                                                |

## Notes

- Fault windows must be longer than the rule's evaluation range and `for` duration (the catalog `window`). The state becomes Alerting (Firing) only after the condition has held for `for`. A **should fire** hypothesis that could not be evaluated because the logged fault window was shorter than that window is a finding about the schedule.
- The day-2 12:00 UTC spike is the saturation-sized one. CPU saturation should show up in metrics alongside the checkout delay. The hypothesis for that slot is still **should fire** on `shop-checkout-p99-latency`. The catalog has no CPU alert rule.
- Informational alerts must not page. They route to a no-page contact point.
- Thresholds remain initial values.

## Known gap

Nothing outside Grafana watches Grafana itself, so Grafana-down is not alerted. That is deliberate because alerts are defined in one place. A second watcher would be another alarm system.
